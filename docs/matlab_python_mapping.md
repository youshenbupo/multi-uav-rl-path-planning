regression data” means data exported or generated by an available MATLAB
baseline must be compared before accepting a Python equivalent. “Unavailable”
does not mean that a result may be invented.

## Phase 4 implementation status

The following fixed-path equivalents are implemented and covered by deterministic
tests under `tests/`. Their numerical regression checks use `rtol=1e-6` and
`atol=1e-8` where the MATLAB fixture provides a directly comparable value.

| MATLAB function | Implemented Python surface | Validation |
| --- | --- | --- |
| `core.terrain_height` | `multiuav.geometry.terrain.terrain_height` | full exported grid plus five MATLAB terrain queries |
| path spherical step geometry | `multiuav.geometry.trajectories.decode_spherical_path` | deterministic Cartesian unit case |
| `core.resample_path` | `multiuav.geometry.trajectories.resample_path` | exported decoded path, 11 samples |
| `core.min_distance_to_cylinder` | `multiuav.geometry.trajectories.segment_to_cylinder_distance` | three exported cylinder segments |
| `core.single_uav_cost` | `MultiUAVEvaluator.evaluate_single` | all seven terms for exported UAV 1 path |
| `compute_spatial_metrics` / `build_conflict_graph` | `MultiUAVEvaluator.evaluate` | exported synchronized-path distance, count, and conflict weight |

`MultiUAVEvaluator.evaluate` does not invoke MATLAB's optional path-repair or
conflict-aware scheduling heuristics. Those are distinct legacy modules and
will be migrated only when a later phase explicitly requires them. This keeps
the evaluator deterministic and prevents hidden mutation of policy outputs.

## Phase 5 implementation status

The deterministic rule-based conflict layer is implemented without GNN, MAPPO,
or CBF code. It uses zero-based UAV identifiers and lexicographic tie-breaking
for public graph edges; the scheduler separately preserves MATLAB's
column-major edge-selection tie behavior.

| MATLAB function | Implemented Python surface | Regression evidence |
| --- | --- | --- |
| `core.build_conflict_graph` | `multiuav.expert.conflict_graph.build_conflict_graph` | synchronized fixture edge `(0, 1)`, squared weight `33600`, 21 samples, minimum distance `10` |
| `core.resolve_conflict_schedule` | `multiuav.expert.temporal_scheduler.TemporalScheduler` | explicit 5-second MATLAB schedule fixture, delayed UAV index 1, no remaining conflict |
| `core.repair_spatial_conflicts` | `multiuav.expert.spatial_repair.SpatialRepairer` | deterministic conflict-center convention, reduced conflict weight, fixed-path cost decreases in both MATLAB and Python |
| coordination composition | `multiuav.expert.coordinator.ConflictAwareCoordinator` | returns paths, delays, graph, logs, and before/after evaluator results |

The local spatial repair preserves endpoints, applies Gaussian lateral and
altitude offsets, then rechecks terrain clearance, world bounds, and cylinder
threat clearance for each changed waypoint. It is a deterministic expert
module, not a learned controller or a replacement for later RL policies.

## Phase 6 implementation status

The HDF5 expert pipeline is implemented in `multiuav.data`. MATLAB reference
episodes retain final paths and schedule outcomes, but have no action-level
logs; consequently their `high_level_action_mask` is false everywhere rather
than containing fabricated labels. Python coordinator replays can explicitly
provide logs and produce masked, attributable high-level labels.

| Source / responsibility | Implemented Python surface | Validation |
| --- | --- | --- |
| MATLAB reference import | `data.matlab_import.import_matlab_reference` | scenario, source seed, raw/repaired paths, delays and nominal speed |
| HDF5 episode schema | `data.expert_schema.write_episode` | fixed `[T,N,*]` time series; flattened waypoint offsets; one graph group per step |
| action and graph conversion | `data.expert_dataset.build_expert_episode` | speed clipping ratios, masks, dynamic features/edges/conflict labels |
| dataset verification | `data.validation.validate_expert_dataset` | finite data, shapes, time, speed, endpoints, graph storage, and evaluator cost replay |
| CLI entry points | `scripts/convert_matlab_experts.py`, `validate_expert_dataset.py`, `visualize_expert_episode.py` | conversion, validation and rendered 3D/top-view smoke check |

The full field and mask contract is documented in
`docs/expert_dataset_schema.md`.

## Phase 7 implementation status

The following surfaces reconstruct the available MATLAB HGALO sequence. They
are deterministic under an explicit NumPy generator seed and keep the source
limitation in their result provenance. They are not a cross-language
CA-HGALO-equivalence claim because the restored MATLAB archive contains no
independent CA-HGALO entrypoint or result artifact.

| Available MATLAB responsibility | Implemented Python surface | Validation |
| --- | --- | --- |
| spherical planning problem / decode | `multiuav.expert.encoding` | S2 exported seed vector matches at `rtol=1e-6`, `atol=1e-8`; endpoint test |
| chaotic population / Lévy step | `encoding.chaotic_initialize`, `alo.levy_flight_step` | fixed-seed numerical repeatability |
| GWO alpha/beta/delta update | `multiuav.expert.gwo.gwo_guided_update` | fixed-seed bounded repeatability |
| ALO local exploitation and adaptive scale | `multiuav.expert.alo.alo_local_exploitation` | fixed-seed bounded repeatability |
| point/path feasibility repair | `multiuav.expert.geometric_repair` | endpoints and shared evaluator replay |
| greedy HGALO evolution / elite history | `multiuav.expert.ca_hgalo.HGALOPlanner` | monotonic global-elite history in seeded integration test |
| final conflict-aware expert output | `scripts/run_ca_hgalo.py`, `generate_expert_data.py` | 5-seed and 30-seed S1 runs; all HDF5 shards validator-replayed |

The 30-seed S1 reconstruction report is stored under
`data/expert/s1_30seed_verified_summary.json` (ignored generated data). It
reports best cost `4009.8338`, mean cost `259041.7705`, strict-success rate
`0.7667`, mean separation `75.9837`, and zero mean temporal conflicts.

## Required migration order

1. Freeze a documented Python data schema and YAML configuration that can
   represent S1--S4 without hard-coded absolute paths.
2. Port environment construction, terrain interpolation, terminal/threat data,
   path encoding/decoding, and basic geometry. Export MATLAB fixtures first.
3. Port and regression-test resampling, cylinder distance, clearance, length,
   turn, and single-UAV cost.
4. Build and validate the multi-UAV evaluator, spatial separation, synchronized
   timing, conflict graph, feasibility result, and experiment record schema.
5. Only after the evaluator is validated, port simple non-RL baselines and
   legacy repair/scheduling modules as required for expert demonstrations.
6. Only after a normal MAPPO train/evaluate loop is validated may later stages
   introduce predictive conflict graphs, hierarchical MAPPO, and CBF filtering.

## Cross-language conventions to lock before coding

- Translate every MATLAB **1-based** index to a named Python 0-based index or
  `slice`; do not store MATLAB indices in Python public data structures.
- Keep all angle calculations in **radian** internally. Convert only explicit
  presentation metrics to degrees.
- Preserve MATLAB's `(N, 3)` row-point convention for NumPy arrays and define
  any PyTorch batch dimension explicitly instead of relying on broadcasting.
- Represent `paths{u}` as `list[NDArray]`, never as an object tensor.
- Store fixed scenario and experiment settings in YAML. A seed must be present
  in every stochastic experiment configuration and result record.
- The source has no CA-HGALO module or CA-HGALO MATLAB regression data. Do not
  name a reconstructed HGALO result as CA-HGALO, and do not claim regression
  until an authoritative CA-HGALO source/export is supplied.
